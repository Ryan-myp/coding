# 部署策略指南

> 从本地开发到生产环境的完整部署方法论

---

## 部署策略选型

```
                    变更频率
        高频 ──────────────────────── 低频
          │                                │
    Feature Flag              Blue-Green / Canary
    + Canary                        │
          │                    重大变更
    Rolling 部署               │
          │                        │
          └──────┬─────────────────┘
                 │
           常规发布
                 │
                 ▼
           Rolling 部署
```

## 1. Feature Flag（特性开关）

**适用：** 新功能渐进发布、AB 测试

```python
# 代码中嵌入开关
def process_payment(amount: float, user: User) -> PaymentResult:
    if use_v2_gateway():  # 特性开关
        return new_gateway_charge(amount, user)
    return legacy_gateway_charge(amount, user)

# 开关配置（独立存储，如 Redis）
FEATURE_FLAGS = {
    "use_v2_gateway": {
        "enabled": False,
        "rollout": 0.0,           # 0% → 10% → 50% → 100%
        "target_users": ["beta_group"],
        "experiments": {
            "v1_vs_v2": {
                "variant_a": 0.5,
                "variant_b": 0.5,
            }
        },
    }
}
```

**开关管理原则：**
- 命名清晰：`use_<feature_name>`
- 设置过期时间，定期清理过期开关
- 不同环境独立配置（dev/staging/prod）
- 关键开关变更需要审批记录

## 2. Canary 发布

**适用：** 新功能验证、风险可控的灰度

```
流量分配：
┌─────────────────────────────────────────────┐
│  Blue (v1)      Canary (v2)    Blue (v1)   │
│  99% ─────────►  1% ──────────►  99%       │
│                                              │
│  监控指标 → 决定是否扩大比例                  │
│  错误率 < 0.1% → 10% → 50% → 100%          │
└─────────────────────────────────────────────┘
```

**Canary 健康检查项：**

| 指标 | 阈值 | 行动 |
|------|------|------|
| 错误率 | > 1% | 停止放量，回滚 |
| p99 延迟 | > 基线 × 2 | 暂停，调查 |
| 业务转化率 | 下降 > 5% | 回滚 |
| 资源使用 | CPU > 80% | 扩容或回滚 |

## 3. Blue-Green 部署

**适用：** 重大版本更新、数据库迁移

```
阶段 1: 部署
  Blue (在线) ──▶ 处理生产流量
  Green (空闲) ──▶ 部署新版本

阶段 2: 验证
  运行冒烟测试
  检查健康指标

阶段 3: 切换
  Router ──▶ Blue (旧)
         ──▶ Green (新) ← 流量切换
         (瞬间切换，可快速回切)

阶段 4: 确认
  观察 30 分钟
  确认无误后销毁 Blue
```

**回滚策略：**
```
切换后立即监控
    │
    ├─ 正常 ──▶ 继续观察
    │
    └─ 异常 ──▶ 立即切回 Blue
               (秒级回滚)
```

## 4. Rolling 滚动发布

**适用：** 常规版本更新

```
Pod1 → Pod2 → Pod3 → Pod4 → Pod5
 │      │      │      │      │
 ▼      ▼      ▼      ▼      ▼
更新 → 更新 → 更新 → 更新 → 更新

同时保持最小可用实例数
maxSurge: 25%   (最多额外 25% 实例)
maxUnavailable: 25%  (最多不可用 25%)
```

## 部署前检查清单

```markdown
## Pre-Deployment Checklist

### 代码
- [ ] 所有测试通过
- [ ] Code Review 完成
- [ ] 无未提交的临时代码

### 配置
- [ ] 环境变量已审核
- [ ] 密钥已通过安全通道注入
- [ ] Feature flags 已检查

### 数据
- [ ] 数据库迁移脚本已验证
- [ ] 回滚脚本已准备
- [ ] 备份已完成（如需要）

### 监控
- [ ] 告警规则已更新
- [ ] 监控面板已准备
- [ ] Runbook 已更新

### 沟通
- [ ] 相关团队已通知
- [ ] 维护窗口已安排（如需要）
```

## 部署后验证

```
1. Health Check ──▶ 服务响应正常
2. Smoke Test ──▶ 关键路径可走通
3. Metric Check ──▶ 错误率/延迟正常
4. Business Check ──▶ 核心业务指标正常
5. User Report ──▶ 无用户反馈异常
```

## 紧急回滚决策树

```
部署后发现问题
    │
    ├─ P0（服务不可用）
    │   └─▶ 立即回滚（不等确认）
    │
    ├─ P1（严重功能损坏）
    │   └─▶ 评估影响范围 → 决定回滚或热修复
    │
    ├─ P2（部分功能异常）
    │   └─▶ 关闭相关 Feature Flag → 继续观察
    │
    └─ P3（轻微问题）
        └─▶ 记录 → 下个版本修复
```
