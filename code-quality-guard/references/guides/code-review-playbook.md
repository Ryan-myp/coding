# Code Review 手册

> 高效 Code Review 的完整指南

---

## Review 流程

### Step 1: 理解上下文

```
在开始 review 之前，回答这三个问题：
1. 这个变更要完成什么？
2. 对应的 spec/任务是什么？
3. 预期行为变化是什么？
```

### Step 2: 先看测试

测试揭示了意图和覆盖：

```
- 有测试吗？
- 测试验证的是行为还是实现细节？
- 边界条件覆盖了吗？
- 测试名称是否描述了预期行为？
- 如果代码变了，测试还能抓到回归吗？
```

### Step 3: 五轴审查实现

对每个变更文件：

```
For each file changed:
1. Correctness: 代码是否做了测试说它该做的事？
2. Readability: 不看作者解释能理解吗？
3. Architecture: 是否符合系统架构？
4. Security: 有无漏洞？
5. Performance: 有无瓶颈？
```

### Step 4: 分类发现

| 前缀 | 含义 | 作者行动 |
|------|------|---------|
| *(无前缀)* | 必须修改 | 合入前必须解决 |
| **Critical:** | 阻塞合入 | 安全漏洞、数据丢失、功能损坏 |
| **Nit:** | 次要，可选 | 作者可忽略 — 格式、风格偏好 |
| **Optional:** / **Consider:** | 建议 | 值得考虑但不必须 |
| **FYI** | 仅供参考 | 无需行动 — 供参考的上下文 |

**排列优先级：** 先说最重要的。不要把真问题埋在 cosmetic nits 下面。

### Step 5: 验证验证

```
- 运行了什么测试？
- 构建通过了吗？
- 是否手动测试了？
- UI 变更有截图吗？
- 有 before/after 对比吗？
```

## 变更规模控制

| 变更大小 | 处理方式 |
|---------|---------|
| ≤100 行 | 一次审查 |
| 100-300 行 | 可接受（单一逻辑变更） |
| 300-1000 行 | 建议拆分 |
| >1000 行 | 必须拆分 |

**拆分策略：**

| 策略 | 适用场景 |
|------|---------|
| Stack | 有顺序依赖 |
| Horizontal | 需要先建共享层 |
| Vertical | 按功能模块拆分 |
| By file group | 跨领域关注点 |

## 多模型审查模式

```
Model A 写代码
    │
    ▼
Model B 审查正确性和架构
    │
    ▼
Model A 处理反馈
    │
    ▼
人工做最终决定
```

## 审查速度

- **响应时限：** 1 个工作日内（目标：当天）
- **大型变更：** 要求作者拆分，而非审查一个巨大变更集
- **快速迭代：** 典型变更应在一天内完成多轮审查

## 处理分歧

1. **技术事实和**数据** 优先于意见和偏好
2. **风格指南** 是风格问题的绝对权威
3. **软件工程原则** 而非个人喜好评估设计
4. **代码库一致性** 如不降低整体健康度可接受

**不接受"以后再清理"** — 经验表明延期清理很少发生。要求在提交前清理，除非真正紧急。

## 诚实审查

- **不要 rubber-stamp** — "LGTM" 没有审查证据毫无价值
- **不要弱化真实问题** — "这可能有点 concern" 当它是生产 bug 时是不诚实的
- **量化问题** — "这个 N+1 查询会在列表中添加 ~50ms/项" 比 "可能慢" 更好
- **对有问题的方法要 push back** — 阿谀奉承是审查中的 failure mode
- **优雅接受 override** — 如果作者有完整上下文且不同意，尊重其判断

## 死代码卫生

重构或实现变更后，检查孤儿代码：

1. 识别不可达或未使用的代码
2. 明确列出
3. **询问后再删除：** "这些已无引用的元素可以删除吗：[列表]？"

```
DEAD CODE IDENTIFIED:
- formatLegacyDate() in src/utils/date.ts — replaced by formatDate()
- OldTaskCard component — replaced by TaskCard
→ Safe to remove these?
```

## 结构性修复建议

当指出结构问题时，给出重构方案而不只是问题：

- **替换条件链** → 用类型模型或分派器
- **合并重复分支** → 提取为单一更清晰的流程
- **分离编排和业务逻辑** → 各自独立可读
- **移出特性特定逻辑** → 放入拥有该概念的包
- **复用规范 helper** → 而非近似的重复
- **使类型边界显式** → 消除下游分支
- **删除透传 wrapper** → 只增加间接层
- **提取 helper 或拆分子模块** → 聚焦职责
