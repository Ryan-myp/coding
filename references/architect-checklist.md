# 架构师检查清单（Architect Checklist）

> 详细版，供深度审查时加载

## 1. 分层架构

### 1.1 标准分层
```
┌─────────────────────────────────────┐
│         Presentation Layer          │  API/CLI/GUI 入口
├─────────────────────────────────────┤
│          Application Layer          │  用例编排、事务管理
├─────────────────────────────────────┤
│           Domain Layer              │  核心业务逻辑、领域模型
├─────────────────────────────────────┤
│         Infrastructure Layer        │  数据访问、外部服务、消息队列
└─────────────────────────────────────┘
```

### 1.2 检查项
- [ ] 各层职责是否单一明确
- [ ] 是否遵循 Dependency Rule（依赖指向核心）
- [ ] 是否有明确的接口隔离（Interface Segregation）
- [ ] 跨层调用是否有合理理由并记录

## 2. 设计模式应用

### 2.1 创建型模式
| 模式 | 适用场景 | 反模式警示 |
|------|---------|-----------|
| Factory | 对象创建逻辑复杂 | 避免在工厂里塞入业务逻辑 |
| Builder | 参数众多且可选 | 避免 Builder 本身成为上帝类 |
| Singleton | 唯一实例（DB连接池等） | 避免滥用导致全局状态 |

### 2.2 结构型模式
| 模式 | 适用场景 | 反模式警示 |
|------|---------|-----------|
| Strategy | 多种算法可切换 | 避免策略类过多无法维护 |
| Adapter | 兼容旧接口 | 避免无限层 Adapter 嵌套 |
| Decorator | 动态增强功能 | 避免装饰器链过长 |

### 2.3 行为型模式
| 模式 | 适用场景 | 反模式警示 |
|------|---------|-----------|
| Observer/PubSub | 事件驱动解耦 | 避免观察者间循环通知 |
| Chain of Responsibility | 责任链处理 | 避免链路过长 |
| Template Method | 骨架固定细节可变 | 避免子类过多 |

## 3. SOLID 原则检查

### 3.1 SRP（单一职责）
- [ ] 每个类/模块是否只有一个 change reason
- [ ] 是否避免了"工具类"上帝类

### 3.2 OCP（开闭原则）
- [ ] 新增需求是否只需添加代码而非修改现有代码
- [ ] 扩展点是否通过接口/抽象暴露

### 3.3 LSP（里氏替换）
- [ ] 子类是否能无缝替换父类
- [ ] 是否有违反前置/后置条件的情况

### 3.4 ISP（接口隔离）
- [ ] 接口是否过于庞大
- [ ] 是否有"胖接口"迫使实现不相关方法

### 3.5 DIP（依赖倒置）
- [ ] 高层模块是否依赖抽象而非具体实现
- [ ] 是否使用 DI 容器或手动注入

## 4. 架构坏味道（Architecture Smells）

| 坏味道 | 表现 | 修复建议 |
|--------|------|---------|
| 意大利面条代码 | 调用关系混乱无规律 | 引入清晰的分层和模块边界 |
| 大球型系统 | 所有模块紧密耦合 | 拆分模块，引入接口抽象 |
| 迷失的哈希 | 找不到代码放在哪 | 建立清晰的目录结构和命名规范 |
| 功能蔓延 | 功能无节制增加 | 引入边界上下文，严格 scope 控制 |
| 脆性基础设施工件 | 改动一处影响多处 | 提取公共逻辑，降低耦合 |

## 5. 扩展性检查

- [ ] 新功能是否只需新增文件而非修改大量已有代码
- [ ] 配置变更是否不需要修改代码
- [ ] 是否有插件化/可插拔设计
- [ ] 是否预留了合理的 Hook/Callback 点
