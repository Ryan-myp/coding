# 通用工程化检查清单（Engineering — Language Agnostic）

> 可读性、可维护性、可测试性通用标准

## 1. 可读性

### 命名
- [ ] 变量名是否表达意图而非类型（`user_count` vs `num`）
- [ ] 函数名是否以动词开头
- [ ] 是否避免了缩写（除非是行业通用）

### 函数设计
- [ ] 函数长度是否合理（Python/Go < 50行，Java/TS < 80行）
- [ ] 函数参数是否 ≤ 4 个
- [ ] 是否遵循单一职责

### 注释
- [ ] 注释说明"为什么"而非"是什么"
- [ ] 公共 API 是否有文档字符串
- [ ] TODO/FIXME 是否有负责人和期限

## 2. 可维护性

### 配置管理
- [ ] 环境差异配置是否外部化
- [ ] 密钥是否通过环境变量/密钥管理获取
- [ ] 业务规则是否可配置

### 错误处理
- [ ] 是否有统一的异常层次
- [ ] 错误信息是否对调用方有意义
- [ ] 是否避免了吞掉异常

### DRY 原则
- [ ] 有无重复代码块
- [ ] 相似逻辑是否提取为公共函数
- [ ] 配置是否有默认值而非处处硬编码

## 3. 可测试性

### 单元测试
- [ ] 每个公开方法是否有测试
- [ ] 测试名称是否描述预期行为
- [ ] 边界条件和异常路径是否有覆盖

### 测试友好设计
- [ ] 是否避免了全局状态和单例
- [ ] 外部依赖是否通过接口抽象
- [ ] 测试数据是否可复用

## 4. 日志规范

- [ ] 日志级别使用恰当（DEBUG/INFO/WARNING/ERROR）
- [ ] 生产日志不包含敏感信息
- [ ] 关键操作有审计日志
- [ ] 日志格式结构化（便于机器解析）

## 5. 文档

- [ ] README 是否清晰说明了项目用途和启动方式
- [ ] API 是否有接口文档
- [ ] 复杂逻辑是否有架构决策记录（ADR）

## 6. 代码审查要点

每次 PR 应包含：
- [ ] 变更目的说明（why）
- [ ] 测试覆盖说明
- [ ] 对现有代码的影响评估
- [ ] 人工 review 后的自测结果
