# 工程师检查清单（Engineer Checklist）

> 详细版，供深度审查时加载

## 1. 可读性

### 1.1 命名规范
- [ ] 变量名是否能准确表达其含义（`user_count` 而非 `uc`）
- [ ] 函数名是否以动词开头（`calculate_total` 而非 `total`）
- [ ] 类名是否使用名词（`PaymentProcessor` 而非 `ProcessPayment`）
- [ ] 常量是否全大写加下划线（`MAX_RETRY_COUNT`）
- [ ] 布尔变量是否使用 `is_`/`has_`/`can_` 前缀
- [ ] 避免使用单字母变量（除了循环计数器 `i`）

### 1.2 函数设计
- [ ] 函数是否只做一件事
- [ ] 函数参数是否 ≤ 4 个（超过则考虑用对象封装）
- [ ] 函数长度是否合理（Python < 50行, Java < 80行）
- [ ] 是否有不必要的抽象（过度设计）

### 1.3 注释规范
- [ ] 注释是否说明"为什么"而非"是什么"
- [ ] 复杂算法是否有思路说明
- [ ] TODO/FIXME 是否有负责人和期限
- [ ] 文档字符串是否完整（函数签名、参数、返回值、异常）

## 2. 可维护性

### 2.1 配置管理
- [ ] 环境差异配置是否外部化
- [ ] 密钥/密码是否通过环境变量或密钥管理服务获取
- [ ] 业务规则是否可配置而非硬编码
- [ ]  Feature Flag 是否用于灰度发布

### 2.2 错误处理
- [ ] 是否有统一的异常层次结构
- [ ] 错误信息是否对调用方有意义
- [ ] 是否避免了吞掉异常（empty except/catch）
- [ ] 关键操作是否有重试和降级机制

### 2.3 日志规范
- [ ] 日志级别使用是否恰当（DEBUG/INFO/WARNING/ERROR）
- [ ] 是否避免了在生产日志中打印敏感信息
- [ ] 关键操作是否有审计日志
- [ ] 日志格式是否结构化（便于机器解析）

## 3. 可测试性

### 3.1 单元测试
- [ ] 每个公开方法是否有对应的测试
- [ ] 测试名称是否描述预期行为
- [ ] 测试是否遵循 AAA 模式（Arrange-Act-Assert）
- [ ] 边界条件和异常路径是否有覆盖

### 3.2 测试友好设计
- [ ] 是否避免了静态方法和全局状态
- [ ] 外部依赖是否通过接口抽象
- [ ] 测试数据是否可复用
- [ ] 是否避免了测试间的隐式依赖

## 4. 代码规范坏味道

| 坏味道 | 表现 | 修复建议 |
|--------|------|---------|
| 魔法数字 | `if status == 3` | 提取为常量 `STATUS_ACTIVE = 3` |
| 重复代码 | 相同逻辑出现多次 | 提取为公共函数/方法 |
| 过长参数列表 | 函数参数 > 4 个 | 封装为参数对象 |
| 过大的类 | 类 > 500 行 | 按职责拆分 |
| 过深的继承 | 继承层级 > 3 层 | 改用组合或设计模式 |
| 死代码 | 未被调用的代码 | 删除或标记废弃 |
